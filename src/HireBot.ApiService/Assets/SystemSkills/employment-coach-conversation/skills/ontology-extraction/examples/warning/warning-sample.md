# warning-sample 评审说明

本文档对应 [warning-sample.json](warning-sample.json)。它的目标不是提供一个可直接落地的高质量 ontology slice，而是专门演示另一类更容易被忽略的情况：结构完全合法、可以通过 schema，但语义上仍然应该进入人工 review。

这类样例的价值在于提醒团队区分两件事：

- `schema 通过` 说明结构没坏
- `值得接受` 还取决于来源质量、概念边界、关系粒度和未决歧义是否足够可控

## 样例定位

- 角色：`WARNING` 黄灯样例。
- 用途：演示什么叫“结构合法，但语义上仍需 review”。
- 适用场景：团队需要训练识别低信任来源、未决歧义和未收敛边界时。

## 使用方式

```powershell
..\..\scripts\validate-slice.py .\warning-sample.json
```

上面的命令适用于当前目录位于 `ontology-extraction` 技能根目录内，调用的是技能目录下的真实校验器；如果需要启发式评审结论，可改用 `--review-mode`。

如果从仓库根目录执行：

```powershell
.\scripts\validate-ontology-slice.py .\src\OpenClaw.Gateway\skills\ontology-extraction\examples\warning\warning-sample.json
```

仓库根目录包装入口只承载普通结构校验，不暴露 `--review-mode`。

---

## 结构层表现

- 结构结果：`PASS`
- 评审状态：`WARNING`
- 当前解读：这份样例结构合法，但命中了多条快速风险信号。

## 对应为什么会得到 WARNING

- 没有任何高信任度来源。
- 存在低信任度来源。
- 冲突和歧义仍处于 `open / deferred`。
- `uncertainties` 非空，说明仍有未决问题。

## 推荐评审方式

1. 先确认 warning 信号分别对应到哪些字段。
2. 再判断这些信号是否会阻断下游消费。
3. 最后决定它是继续作为草案保留，还是需要补证据后再收紧。

## 建议评审结论模板

- 结构合法性：已通过 schema 校验
- 评审状态：`WARNING`
- 当前结论：适合作为黄灯讨论样例，不建议直接作为最终本体沉淀

## 最适合怎么用

- 作为黄灯讨论样例
- 作为 review 训练材料
- 作为“结构通过不等于语义达标”的示例

## 详细内容

### 这个样例为什么会通过 schema

它能通过，不是因为内容已经足够强，而是因为它满足了当前 schema 关注的结构约束：

- 根字段齐全，没有缺字段
- 所有枚举值、常量值、ID 格式、日期格式都合法
- 概念、关系、约束、来源之间的引用链没有断裂
- 没有额外字段，也没有明显类型错误
- 冲突、歧义、不确定项都被显式记录，而不是被静默省略

也就是说，schema 证明的是“这份 slice 至少是一个格式稳定、字段自洽的产物”，而不是“这份 slice 的领域建模质量已经足够高”。

---

### 为什么它仍然应该 review

下面这些点都不会让 schema 失败，但在真实协作里都足以触发黄灯。

### 1. 来源可以追溯，但证据强度不够

样例里只有两个来源：

- `S1`：高层架构文档，`trust_level = medium`
- `S2`：综合说明文档，`trust_level = low`

这意味着来源并非“不可用”，但它们更多是产品或架构层说明，而不是直接定义 ontology 边界的强证据。尤其 `S2` 明确注明“部分术语偏面向用户而非本体定义”，这本身就是黄灯信号。

评审时要问的不是“有没有来源”，而是：

- 这些来源是否足以支撑概念定义，而不只是支撑叙述性说明。
- 是否还缺少代码、配置、schema 或更接近事实源的材料。

### 2. 概念存在，但边界仍然偏粗

`C1 = 代理能力` 和 `C2 = 工具执行` 都是合法概念，但它们当前的定义粒度明显偏粗：

- `代理能力` 还没有说明它是抽象能力集合、配置能力，还是运行时能力快照。
- `工具执行` 虽然被标记成 `event`，但没有进一步区分同步、异步、审批前、审批后、失败重试等关键语义。

这类问题不会让 JSON 结构失效，但会显著影响后续复用。如果团队拿这份 slice 继续生成代码、提示词或评审结论，语义漂移风险会很高。

### 3. 关系合法，但谓词表达过宽

`R1` 使用了 `depends_on`，这在 schema 层完全合法，但它其实是一个很宽的关系：

- 没说明依赖发生在哪个阶段
- 没说明是不是所有代理能力都成立
- 没说明是否存在无需工具即可成立的例外

这也是为什么样例里专门放了约束 `K1`，明确禁止把当前关系误读成“完整执行语义”。

换句话说，关系字段填得合法，不代表关系本身已经足够精确。

### 4. 歧义被记录了，但并没有被解决

这个样例是有意识地把歧义写出来，而不是假装已经澄清：

- “代理能力”是抽象集合还是实例快照，仍然 `open`
- “工具执行”应该是事件、服务能力还是流程节点，仍然 `deferred`

这是好事，因为至少没有隐瞒问题；但它同时也说明这份 slice 暂时不能被误认为“稳定本体”。

评审时应该把“歧义是否已显式记录”和“歧义是否已收敛”分开看。前者做得对，不等于后者已经完成。

### 5. 不确定项说明了缺口，但缺口仍需补证据

`uncertainties` 里明确指出：是否要把审批、权限和工具选择策略拆成独立概念层，目前证据不足。

这说明样例已经知道自己哪里不完整，但“知道不完整”本身不能替代补证据。它只是在流程上合格，在结论上仍是暂定状态。

### 6. 下一步动作存在，说明当前版本还不是终态

`next_actions` 里要求：

- 补一个高信任度代码来源
- 先定义“代理能力”到底是哪一层概念

如果一个 slice 还依赖这些前置动作才能稳定，那么它就应该被当作“可讨论草案”而不是“最终可沉淀本体”。这不是错误，但必须在评审结论里说清楚。

---

### 对应触发了哪些 warning 信号

如果运行下面这条命令：

```powershell
..\..\scripts\validate-slice.py .\warning-sample.json --review-mode
```

脚本会给出 `Heuristic verdict: WARNING`。这个结果不是抽象判断，而是能和当前样例里的具体字段一一对照。

### 当前命中的 warning 信号

| warning 信号 | 当前样例中的对应位置 | 为什么命中 |
| --- | --- | --- |
| 没有任何 `trust_level = high` 的来源 | `sources[0].trust_level = medium`，`sources[1].trust_level = low` | 两个来源里没有一个是 `high`，说明当前切片缺少高信任度事实源。 |
| 存在 `trust_level = low` 的来源 | `sources[1].trust_level = low` | 样例明确保留了一个低信任来源，用来演示“有来源”不等于“来源足够强”。 |
| 存在 `status = open` 或 `status = deferred` 的冲突 | `conflicts[0].status = deferred` | 这说明冲突被记录了，但还没有真正收敛。 |
| 存在 `status = open` 或 `status = deferred` 的歧义 | `ambiguities[0].status = open`，`ambiguities[1].status = deferred` | 两个核心歧义都还处在未最终解决状态。 |
| `uncertainties` 数组非空 | `uncertainties[0]` 存在 | 样例明确承认还有结构外的未决问题，需要补证据或补用户输入。 |

### 为什么这些信号会把它推到黄灯而不是失败

这些信号表达的是“语义风险仍在”，不是“结构已经损坏”：

- 它的 JSON 结构仍然合法
- 它的引用链仍然闭合
- 它的字段仍然符合 schema
- 但它保留了足够多的未决问题，所以不适合直接当最终本体沉淀

换句话说，`WARNING` 的含义不是“这份 slice 错了”，而是“这份 slice 现在更适合拿来 review，而不是直接拿来定稿”。

### 脚本输出和人工评审怎么配合

推荐按下面顺序理解：

1. 先看 `Structure: PASS`，确认它不是结构错误。
2. 再看 `Heuristic verdict: WARNING`，确认它命中了快速风险信号。
3. 最后回到本页上面的分析和 `../../references/REVIEW_CHECKLIST.md`，判断这些风险是否足以阻断下游使用。

所以这份样例最合适的定位仍然是：

- 可通过 schema
- 会触发 warning
- 适合作为黄灯讨论样例
- 不适合直接视为最终稳定本体

---

### 详细评审方式

评审 `warning-sample.json` 时，建议不要只问“能不能过校验”，而是至少补问下面几类问题：

1. 当前来源是否足以支撑概念定义，而不只是支撑描述性语言。
2. 当前概念是否已经收敛到稳定边界，还是仍停留在泛化标签层。
3. 当前关系谓词是否足够精确，能否直接指导实现或文档生成。
4. 当前记录的歧义和不确定项，是否会阻断后续下游消费。
5. 这份 slice 当前适合作为“评审草案”、“参考草案”还是“正式沉淀结果”。

---

### 详细评审结论模板

可以直接按下面口径记录：

- 结构合法性：已通过 schema 校验
- 来源质量：可追溯，但证据强度仍不足以支撑完整定型
- 概念边界：可工作，但粒度偏粗，仍需收紧
- 关系精度：可表达高层依赖，但不足以支撑完整执行语义
- 当前结论：适合作为黄灯样例或讨论草案，不建议直接作为最终本体沉淀

---

### 详细使用建议

- 向团队演示“通过校验”和“通过评审”是两道不同关卡
- 在 onboarding 时解释为什么 ontology slice 不能只看 JSON 是否合法
- 作为 review 训练样例，让团队练习识别低信任来源、过宽概念和未收敛关系
- 作为 CI 之外的人审补充案例，提醒结构校验不能替代语义判断
