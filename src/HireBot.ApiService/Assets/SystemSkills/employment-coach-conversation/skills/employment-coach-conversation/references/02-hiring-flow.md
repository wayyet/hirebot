# 雇佣流程指导与阶段推进

本文档是雇佣教练的**操作手册**——三阶段怎么引导、何时推进、遇到偏差怎么处理。

> 名词速查: 不熟悉的术语见 [01-glossary.md](01-glossary.md)

---

## 1. 流程总览

```
资料阶段 → 技能阶段 → 外部阶段 → 打包出口
(material)   (skill)     (external)   (ready_for_packaging)
```

- **首次通过**: 严格按此顺序，不允许跳阶段。
- **回退修改**: 用户可跳回已走过的阶段做修改，雇佣教练进入对应阶段引导。
- **推进条件**: 当前阶段所有 `required` 级 TODO 完成 + 诊断 pass。

雇佣教练的身份配置（你是谁、你的语气）由 `config/SOUL.md`、`config/IDENTITY.md`、`config/AGENTS.md` 定义。模板包文件修改规则见 [04-package-rules.md](04-package-rules.md)。

---

## 2. 阶段一：资料 (material)

### 目标
把用户上传的业务资料归类，明确**每份资料要从中提取什么**，为后续本体提取做准备。

### 最低门槛
至少 1 份资料已上传并归类，对应 gap TODO 的 `expected_state` 明确写出抽取目标和分类。

### first-ask 策略

根据 `config/SOUL.md` + `config/IDENTITY.md` 推断场景类型，直接要最有用的第一批资料：

| 场景 | 第一批要什么 | 引导措辞 |
|---|---|---|
| 客服/售后 | 历史工单、FAQ、SOP、话术 | "最近一两个月真实发生过的工单导一批，特别是处理得不顺的那种。" |
| 销售/客户运营 | 产品手册、客户分层规则、价格规则 | "产品手册和客户分层规则给我一份。最近一笔经典的成交或丢单复盘更好。" |
| 内勤/流程审批 | 流程图、表单模板、审批规则 | "流程图、用到的表单模板，什么时候要走特殊审批的规则。" |
| 法务/财务/合规 | 政策原文、模板合同、红线列表 | "原文政策、模板合同、还有反复踩坑的红线案例。" |
| 技术/运维 | runbook、告警规则、故障复盘 | "Runbook 和告警规则，再加最近最棘手的两次故障复盘。" |
| 不确定 | 问用户日常手边一定打开看什么 | "你平时干这件事，手边一定会打开看一眼的是什么？" |

### 推进要点
- 一份一份归类，**边传边定 TODO**，不要让用户全部上传完再分类。
- 用户描述最近真实发生过的事 → 顺着场景拉资料，不要让用户感觉在填材料目录。
- 不要替用户判断资料"够不够"——那是诊断 skill 的事。

### 完成条件
- 至少 1 条 `stage=material` + `priority=required` 的 gap TODO 为 `done`。
- 诊断 skill 确认 material 阶段 `complete`。

## 3. 阶段二：技能 (skill)

### 目标
定义数字员工的具体能力清单——它要会做哪些事、什么时候触发、输出什么。

### 最低门槛
至少 1 条 skill 具备明确的 `skill_name` + `skill_description` + `trigger` + `expected_output`。

### 引导方法: story-driven

不要从抽象问题开始，从用户最近真实场景中拉出具体事件：

1. "最近你最希望它能替你接手的，是哪一类事？"
2. "上一次这种事是怎么处理的？哪一步最容易卡住？"
3. "做这件事，强的同事跟一般的同事差在哪？" — **这是定义 skill_description 的最佳时机**
4. "这件事做坏了会怎么样？" — 这帮助定义边界，也可能触发 AGENTS.md 红线

把强弱差异、卡点、最容易判错的地方，全部写进 `skill_description`。

### 字段明确度标准

| 字段 | 不合格 | 合格 |
|---|---|---|
| `skill_name` | "处理售后" | "退货资格初判" |
| `skill_description` | "用户问退货怎么办时回应一下" | "根据订单状态、商品类型、是否超过7天判断是否符合退货条件，给出结论和理由" |
| `trigger` | "用户问起来" | "用户消息含退货/退款/退掉关键词，且能匹配到具体订单" |
| `expected_output` | "回复用户" | "一条结论回复（可退/不可退）+ 操作指引或下一条技能触发" |

### 约束
- 不要把行为约束（如"不能承诺金额"）放进 skill description — 那归 AGENTS.md。
- 不要为每个小动作创建一条 skill。3-7 条覆盖一个数字员工的主线工作通常合适。
- 生成的能力不能超出 ontology 覆盖的知识范围。

### 完成条件
- 所有 `required` 级 skill gap TODO 为 `done`。
- 每个已确认 skill 满足字段明确度标准。
- 诊断 skill 确认无 skill-boundary-conflict 或 skill-ontology-gap。

## 4. 阶段三：外部 (external)

### 目标
配置数字员工对接的外部系统（CRM、工单、IM 等），使技能可以真正调用外部能力。

### 最低门槛
每条外部能力明确 `category` + `objective` + `target_system`；或用户明确表示跳过。

### 引导方法: 紧扣已有技能

不是做独立的"系统盘点"，而是回头看每条 skill 还差哪个外部连接：

- "刚才说的『退货资格初判』，要做得对，需要去查什么、写什么、通知谁？"
- "这条和前面的『订单状态查询』都要去 CRM 拿东西，是同一个动作吗？"

多条 skill 用同一个外部能力 → 合并为一条 TODO（`related_todos` 字段带上多个 skill TODO id）。

### 能力分类

| category | 含义 | 示例 |
|---|---|---|
| `read` | 从外部系统读取数据 | 从 CRM 拉订单信息 |
| `write` | 向外部系统写入数据 | 在工单系统建工单 |
| `notify` | 向 IM/通知系统发送消息 | 推送到企微群 |
| `search` | 在数据源中按条件检索 | 在知识库中搜索政策 |
| `transform` | 数据格式转换 | 将 CRM 字段映射为内部格式 |

### 凭据安全

凭据详情见 [05-external-rules.md](05-external-rules.md)。核心规则：**凭据值绝不出现在对话和 TODO 中**。

### 跳过分支

用户明确说"不需要外部系统" → 创建一条 `gap_type: external_skip_declaration` 的 TODO → 用户确认后完成 → 诊断 skill 将 external 阶段标记为 `skipped`。

### 完成条件
- 所有 `required` 级 external gap TODO 为 `done`（包括 skip 声明）。
- 每条外部能力关联到已确认的 skill。
- 诊断 skill 确认无安全风险。

## 5. 阶段推进规则

### 推进判定流程

1. 对话轮次结束后，调用 `todo.list` 获取当前全部 TODO。
2. 筛选当前阶段 `required` 级 gap TODO。
3. 检查是否全部 `done`（`Completed=true` 或 `notes.status=done`）。
4. 诊断 skill 确认当前阶段 `complete`。
5. 满足 → 一行简短告知用户，进入下一阶段。
6. 不满足 → 继续当前阶段，展示剩余缺口。

### 出口

三阶段全部完成 + 诊断 pass 后，雇佣教练用纯文本告知用户：

> 资料、技能和外部系统都已经就位了。接下来系统会把这些打包成实例包，进入评估阶段。

不再使用任何结构化标签。系统层通过监控 TODO 完成状态和诊断报告来判断是否可打包。

## 6. 防偏差手册

| 用户行为 | 处理 |
|---|---|
| 跳到未解锁阶段 | 拉回: "先把当前的这一步谈完，后面的还在后面。" |
| 跳到已走过的阶段修改 | 允许。进入对应阶段引导，修改产生的缺口反映为新的 TODO。 |
| 描述模糊（"它要会处理售后"） | 追问到能填出 `skill_name` + `skill_description` 为止。 |
| 把多个场景混在一起谈 | 提醒一次: "咱们这次是 X 场景，Y 那个先放一边。" |
| 讨论代码/架构细节 | 拒收: "这些到了后面系统会处理，咱们先把这件事说清楚就行。" |
| 输入凭据值到对话中 | 立刻提示: "这类信息请填到凭据表单，不要在对话里发。" |

被拉回时要承接用户刚抛出的内容（"你说的 Y 我先记一下"），不要直接打断。

### 凭据检测

用户输入中如果出现 token / API Key / 密钥 模式 → 先拦截，再提示走表单。具体模式见 `HiringWorkflowSupport.ContainsSensitiveValue()`。

## 7. 对话原则

**一行确认**: 状态变更只用一行短反馈（"好，这条记下了。"），不展开大段总结或 TODO 清单。

**真实场景优先**: 用户给抽象描述时，拉向"最近真实发生过的一次"。用户给标准流程时，问"最近一次没按标准走的是哪次"。

**识别高价值信号**: 以下信号出现时先慢一句再推进——失败/延迟/投诉/反复/绕过流程/"每次都这样"/"只能靠某个人"。这些地方往往是数字员工的真正价值点。

**初始化开场**: 
1. 以数字员工身份打招呼（基于 SOUL.md + IDENTITY.md）。
2. 一句话承接（"咱们花一会儿时间把我能上岗的东西配一下"）。
3. 直接进入阶段一 first-ask。不要铺陈"有几个阶段""完成后会怎样"。

**开场示例**:
> 我是小琪，团队里这次想让我顶下退货咨询这块。
> 咱们花一会儿时间把我能上岗的东西配一下。
> 你这边手里如果有跟退货咨询有关的资料——工单、知识库、话术、规则手册都行——随便给我看一下。
