# 场景类型与资料引导

不同的数字员工角色，第一批最该看的资料不一样。先从 soul.md / identity.md 推断当前场景类型，再决定开口要什么。**目的不是覆盖所有资料分类，而是用最自然的方式让用户拿出最有用的第一批**。

## 场景类型 → first ask 对照表

| 场景类型推断 | 第一批最该让用户拿出来的资料 | 引导措辞参考 |
|---|---|---|
| 客服 / 售后 / 工单 | 真实历史工单（特别是处理不顺的那批）、FAQ、SOP、话术模板 | "最近一两个月真实发生过的工单导一批给我，特别是那种处理得不顺的——那种最有用。" |
| 销售 / 客户运营 | 产品手册、客户分层规则、价格 / 折扣规则、典型话术、竞品对比 | "产品手册和客户分层规则给我一份。如果有最近一笔比较经典的成交或丢单复盘，更好。" |
| 内勤 / 流程审批 | 流程图、表单模板、审批规则、异常处理说明 | "流程图、用到的表单模板，还有什么时候要走特殊审批的规则，先看这些。" |
| 营销 / 内容 | 品牌调性、模板库、过往爆款 / 翻车案例 | "品牌调性的说明先看一眼，然后挑两三个跑得最好和最差的案例对比给我看看。" |
| 法务 / 财务 / 合规 | 政策原文、模板合同 / 单据、红线列表、典型违规案例 | "原文政策、模板合同（或单据）、还有反复踩坑的红线案例，先这些。" |
| 技术 / 运维 | runbook、告警规则、系统拓扑、典型故障复盘 | "Runbook 和告警规则先给我，再加最近三个月最棘手的两次故障复盘。" |
| 不在以上分类 / 模糊 | 不要硬猜——问一句：用户日常处理这件事时，手边一定要打开看的是什么 | "你平时干这件事，手边一定会打开看一眼的是什么？那个先给我。" |

## 判定原则

- 先从 identity.md 的 role / mission 字段、soul.md 的核心使命定位场景
- 文本含混时（如"行政助理"既可能是审批也可能是内勤），按场景类型再问一句确认，不要替用户挑
- 用户给的资料如果跟推断的场景类型不匹配（如客服员工被丢过来一份合同模板），追问一句而不是默认接受
- 一旦确认推断错了（"原来你这其实是合规岗"），**静默修正所有 `drafting` / `ready_to_dispatch` 状态 todo 的 `scene_hint` 字段**，不必专门通知用户；已 `dispatched` / `confirmed` 的 todo 保留原值用于追溯，新建 todo 用新值。让用户感觉对话只是在跟着他的真实场景走，不需要"承认刚才弄错了"

## Story-driven 推进（阶段 1）

收齐第一批资料的过程不要让用户感觉像在填材料目录。用一个真实场景把对话粘起来：

- "最近一次这件事最难办的是哪种情况？" → 用户讲一段
- "刚才你说的那种情况，跟它有关的资料、规则、模板，能找到吗？" → 顺着场景拉资料
- "这份是 SOP、规则手册、还是历史案例？你最希望它从里面学到什么？"

资料一份一份归类，**边传边定 todo**，不要等用户全部上传完再分类。每收到一份资料就更新对应的 handoff todo，让用户看到"它确实在收"。

如果用户的故事里出现情绪信号（投诉、反复、没办法），就在那个点上多问一句，不要直接推进到下一份资料——那一处往往就是最有价值的本体抽取目标。情绪信号识别详见 [interaction-quality.md](./interaction-quality.md)。

## 阶段 1 追问到什么程度才算够

- 资料的业务定位（SOP / 规则 / 案例 / 产品手册 / 流程图 / 历史对话 / 其他）
- 用户希望从中获得什么（业务对象定义 / 决策规则 / 边界与约束 / 话术风格 / 场景案例）

## 阶段 1 不要做的事

- 不要描述"本体切片长什么样"
- 不要替用户判断资料"够不够"——这是诊断 skill 的事
- 不要用"资料齐全度"、"覆盖率"这种数据化语言压人，用"这一类咱们先这些，后面不够再补"的口气

阶段 1 handoff todo 的字段定义、明确度判定、dispatch 时机详见 [handoff-todo-schema.md](./handoff-todo-schema.md) 阶段 1 部分。
